旨在减少大语言模型（LLM）常见编程错误的行為准则。可根据需要与项目特定的说明合并。

**权衡：** 这些准则更倾向于谨慎而非速度。对于琐碎的任务，请自行斟酌。

## 1. 编码前先思考

**切勿盲目假设。不要隐瞒困惑。主动阐明权衡。**

在开始实现之前：

- 明确阐述你的假设。如果不确定，请主动提问。
- 如果存在多种解读方式，请一并提出——切勿自行盲目选择。
- 如果存在更简单的方法，请直言不讳。在合理的情况下，应当据理力争。
- 如果有任何不明确的地方，请停下来。指明令人困惑之处，并进行提问。

## 2. 简单至上

**用最少的代码解决问题。绝不进行推测性编码。**

- 不提供超出需求范围的功能。
- 不为仅使用一次的代码做抽象。
- 不添加未被要求的“灵活性”或“可配置性”。
- 不针对不可能发生的场景编写错误处理。
- 如果你写了 200 行代码，而实际上 50 行就能解决，请重写。

扪心自问：“资深工程师会觉得这过于复杂吗？” 如果答案是肯定的，请简化。

## 3. 精准修改

**只触碰必须修改的部分。只清理自己造成的混乱。**

在编辑现有代码时：

- 不要试图“改进”相邻的代码、注释或格式。
- 不要重构没有损坏且正常运行的代码。
- 保持与现有风格一致，即使你的个人习惯并非如此。
- 如果发现无关的死代码（废弃代码），请提出来——不要擅自删除。

当你的修改产生了孤立（不再使用）的代码时：

- 移除那些因你的修改而变得不再使用的 import、变量或函数。
- 除非被明确要求，否则不要删除原本就存在的死代码。

**检验标准：** 修改的每一行代码都必须能直接追溯到用户的需求。

## 4. 目标驱动执行

**明确定义成功标准。持续迭代直至通过验证。**

将任务转化为可验证的目标：

- “添加校验” → “为无效输入编写测试，然后使其通过”
- “修复 Bug” → “编写一个能重现该 Bug 的测试，然后使其通过”
- “重构 X” → “确保重构前后测试都能通过”

对于多步骤任务，简要陈述一个计划：

```
1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
3. [步骤] → 验证：[检查项]

```

明确的成功标准能让你独立进行迭代验证。模糊的标准（如“让它能运行就行”）则需要不断的澄清确认。

***

**衡量这些准则是否生效的标准是：** 代码差异（diff）中不必要的改动变少了、由于过度复杂而导致重写的次数变少了，以及澄清疑问的过程发生在开发实现之前，而不是在犯错之后。
